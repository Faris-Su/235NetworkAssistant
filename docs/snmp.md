# SNMP 模块与 OID 支持清单（Source of Truth）

> 依据：外部提供的设备 SNMP Walk 样例（原始数据不随项目发布；设备型号、地址与规模信息已省略）。
> 该 walk **只覆盖锐捷私有企业分支 `1.3.6.1.4.1.4881.1.1.10.2.*`**，
> 标准 MIB-II（`1.3.6.1.2.1.*`）**一条都没有** —— 所以设备名等信息不能照搬通用 OID。
>
> 规则：**walk 里没有的 OID 一律不加**；含义不能确认的标 `推断/未确认`，界面明确标注，不冒充确认值。
> OID 字符串只允许出现在 `Services/Snmp/SnmpOidRepository.cs` 与 `SnmpQueryService.cs`，
> View / ViewModel / XAML 里禁止出现裸 OID。

## 1. 查询架构（与 CLI 完全解耦）

### 1.1 OID 来源策略（现场实机反馈后修正）

脱敏 Walk 样例只覆盖厂商私有分支，**缺少两样东西**，必须用标准 MIB 补：

| 需要的信息 | 私有 walk 的情况 | 正确来源 |
| --- | --- | --- |
| 设备名称 | **没有任何 SysName**；早期误用私有分支里的 Community（值就是监控团体名）当设备名 | 标准 MIB-II `sysName` `1.3.6.1.2.1.1.5.0` |
| 接口清单 | `.105` 是**光模块 DDM 表**，不能代表完整物理接口清单 | 标准 IF-MIB `ifName/ifDescr` + `ifXTable` |
| 接口状态/流量 | 私有列含义未确认 | 标准 `ifAdminStatus/ifOperStatus/ifHighSpeed/ifHCInOctets/ifHCOutOctets/ifInErrors/ifOutErrors` |

规则：**标准 MIB-II / IF-MIB 优先**（RFC 1213 / RFC 2863，交换机必须实现，含义由 RFC 定义）；
锐捷私有 OID 只用于标准 MIB 没有的信息（型号 / 序列号 / CPU·内存 / 温度 / 风扇 / 电源 / VLAN / MAC / ARP）。

### 1.2 表类信息一律用 WALK（现场故障根因）

现场反馈"温度 / 风扇 / 电源都取不到"。根因不在 OID，而在**取值方式**：

```
旧实现：按固定索引 GET（.44.1.5.1.0.1、.44.1.5.1.0.2 …）
        不同型号的传感器数量 / 索引写法不同（.0.1 / .1 / 没有）
        → 只要有一个索引设备不认识，SNMP 代理就对**整批请求**回 noSuchName
        → 整张表变空（用户看到的就是"温度风扇电源都没取到"）

现实现：WALK（GETNEXT）整张表
        → 不存在的子树只会正常结束，且自动适配任意索引与传感器数量
        → 再加一层兜底：GET 收到 noSuchName 时逐个 OID 重问，能取到的就留下
```

> **本次纠错（2026-09-19）**：内存三列**不再自动探测列号**——设备 Walk 中存在不同单位的候选列组，
> 两组都满足"已用+剩余=总量"时，自动探测可能把 KB 数值误当成 MB（D1）。
> 现在写死 12/13/14 并标注单位 MB，取不到就 N/A。
> CPU 改为**标准 HOST-RESOURCES-MIB `hrProcessorLoad`**；锐捷私有 CPU 百分比列（50/22/50）含义从未被证实，
> 已从界面移除（详见 §6 纠错记录）。

```
SNMP 页（IP + Community + UDP 161）
   → SnmpQueryService
      → SnmpV2cClient（自实现 BER，GET / GETNEXT-WALK）
         → UDP → 设备

CLI 链路（连接页 / CLI 页 / 各 show 页面）
   → ConnectionService → Serial / Telnet → 设备
```

两者只在 UI 层共享"当前设备 IP"（[使用当前设备 IP] 按钮），底层通信完全独立：
SNMP 页不要求 Console / Telnet / SSH 已连接。

## 3. 性能与刷新策略

- 标量与固定索引表（资源 / 温度 / 风扇 / 电源）**一次 GET 打包**（每报文 ≤ 12 个 OID）；
- 变长表（接口 / VLAN / MAC / IP）用 **WALK**，并设行数上限：接口 128 行、VLAN 512 行、MAC 2048 行、ARP 1024 行，
  超出标"已截断"；
- 自动刷新默认 **OFF**，间隔 5 秒步进（5/10/15/20/30/60/120）；**单实例查询、上一轮未完成则跳过本轮**；
- 全程 async/await，不用高频 Timer、不为每个 OID 建线程。

## 4. 安全

- Community 只存在内存（`AppServices.Snmp.Community`），**不写日志、不写 settings.json、不进设备信息库**；
- 设备信息库（`%LocalAppData%\235NetworkAssistant\snmp-devices.json`）只保存查询结果与时间戳。
  界面入口在 **【SNMP】页底部**的「SNMP 信息库」面板（顶栏 [信息库] 一键展开）；
  V0.2.1 起由【设备】页迁移过来，数据文件与格式不变（见 `docs/architecture.md` §17.14.1）；
- 所有密码类输入框（Telnet 密码 / Enable 密码 / SNMP Community）默认显示为 `••••`，
  提供 👁 显示/隐藏按钮，按钮只切换当前输入框的显示方式，不改变保存值。

## 5. 自动化验证

`work/selfcheck` 内置 SNMP 模拟代理（UDP，支持 GET + GETNEXT 与"错误 Community 不回应"），覆盖：
不连 CLI 直接查询 / 正确 Community / 错误 Community / IP 不可达 / 单个 OID 缺失 / 多表查询 /
自动刷新 OFF 不发包 / ON 后按间隔刷新 / 慢查询不重叠 / 两台设备分别保存 / Community 不落盘 /
密码显示按钮。发布件端到端：`work/snmp_page_test.js`（`--ui-page=snmp`）。

**纠错后新增的回归场景**（模拟代理现在按真机 walk 喂数据，含干扰列）：

| 场景 | 断言 |
| --- | --- |
| D1 内存回归 | 内存行**同时**给两组不同单位列；界面使用正确 MB 组，且不得把 KB 值误当 MB |

### 6.4 第二轮修复（依据外部设备 Walk 样例；具体地址与型号已省略）

#### 6.4.1 真机 walk 回放验收（2026-09-20）

使用外部设备的完整 Walk 样例（GETBULK 采集，只读），接进自检做**回放式回归**（不再是手挑子集——那正是"自检全绿、真机出错"的根因）。

`work/selfcheck` 场景「SNMP：真机 walk 回放」实测结果：

| 位置 | 真机 walk 里的值 | 界面显示 | 结论 |
| --- | --- | --- | --- |
| 内存（KB 组） | `.35.1.1.1.{6,7,8}.1` = 示例 KB 值 | **按 MB 正确换算** | ✅ KB→MB 换算正确 |
| 内存使用率 | 设备值与计算值接近 | 设备值优先展示 | ✅ 采信设备值（±3pp 规则） |
| CPU | `.36.1.1.{1,2,3}.0` 与后续列返回样例值 | 按设备字段显示 | ✅ 私有表主路径 |
| CPU 每卡 | `.36.1.2.1.2.1` = 示例标识 | 按设备字段显示 | ✅ |
| 风扇 | 风扇表返回模块名称与状态原始值 | 按原始值展示并标注未确认 | ✅ 新根路径生效 |
| 接口 MAC | `ifPhysAddress` = 示例原始字节 | **规范化 MAC 地址** | ✅ 原始字节 |
| ARP VLAN | `.2.1.1.1.1` = ifIndex；`ifDescr` = VLAN 接口名 | **解析后的 VLAN ID** | ✅ 还原成 VLAN ID |
| 温度 | 全树无温度对象 | **N/A + "该型号未提供私有温度表"（Unsupported）** | ✅ 不误报、不算失败 |
| 总体状态 | — | **查询成功：支持项正常展示，未提供项明确标注** | ✅ 不是"部分成功" |

另外用同一份 Walk 样例确认了两件事：
1. 某些软件版本可能没有 `.12/13/14`（MB 列）→ 候选列组（MB→KB）的设计是必需的；
2. 风扇表里同时存在 **`-255` 哨兵值**（第 11 列）和 `"-"`、空 `Hex-STRING` 占位 → 与《学会获取与读懂OID》§2.6 的实测一致。

**GETBULK 状态（2026-09-20 更新）**：报文构造 / 多 varbind 解析 / 单调前进保护 / 退化 GETNEXT 都已实现。
当时**默认关闭**（`SnmpV2cClient.BulkEnabled = false`）的原因是"手头的模拟代理没有一个真正正确实现 0xA5"，
现在这条已经补上并且**被独立实现交叉验证过**，同时**顺着它查出一个真 bug**（见 §6.6）。
默认值仍然保持关闭，剩下的一步是"在一台真机上比过 GETBULK 与 GETNEXT 逐条一致"——**需要现场 UDP 161 通路**。

| 编号 | 现场现象 | 处理 |
| --- | --- | --- |
| P0-1 | 内存"未取到"：不同版本的资源表列号不同，固定列可能返回 noSuchObject | 改成**候选列组**：`{12,13,14}` MB → `{6,7,8}` KB（÷1024，向下取整）；两组都凑不齐才 N/A。概览卡不再固定 GET，改为 WALK 资源表后走同一份 `ResolveMemory`（铁律 5 仍成立） |
| P0-4 | MAC 按文本解码时可能出现乱码 | `SnmpValue` 增加 `Bytes`（OCTET STRING 原始字节）；接口 / MAC / ARP 三处统一走 `MacAddressHelper.FormatBytes` |

### 6.6 第四轮修复（2026-09-20）：GETBULK 的 OID 比较错误（会让表格静默截断）

**背景**：GETBULK 一直关着，理由是"没有合规的 0xA5 代理可比对"。这一轮把这条堵点补掉，并顺着它查出一个真 bug。

#### 6.6.1 先把"合规代理"补上，而且用第三方实现交叉验证

- 自检代理 `MockSnmpAgent` 原来只认 `0xA0`(GET) / `0xA1`(GETNEXT)，收到 `0xA5` **直接不回**。
  现在按 RFC 3416 实现：`non-repeaters` / `max-repetitions` 复用 `error-status`/`error-index` 两个字段，
  每个重复组连续取 maxRepetitions 个后继，走到树尾补 `endOfMibView`。
- **不能只用"我们的客户端 ↔ 我们的代理"自证**（两边可能错得一样）。所以用 npm 的
  **net-snmp 3.29.1（独立实现）** 当客户端，分别用 GETNEXT 与 GETBULK 走我们代理的同一棵子树，逐条比 OID/类型/值：

| 子树 | 结果 |
| --- | --- |
| 系统组 `1.3.6.1.2.1.1` | 6 / 6 条，逐条一致 |
| 标准 IF-MIB ifName `1.3.6.1.2.1.31.1.1.1.1` | 多条记录，逐条一致 |
| 标准 IF-MIB ifTable `1.3.6.1.2.1.2.2.1` | 多条记录，逐条一致 |
| 私有风扇表 `.42.1` | 多条记录，逐条一致 |
| 私有 VLAN 表 `.9.1.7.1` | 多条记录，逐条一致 |
| 私有接口表 `.10.1.1.1` | 多条记录，逐条一致 |
| 私有 MAC 表 `.22.1.1.5.1` | 多条记录，逐条一致 |

复跑：`node work/verify_agent_bulk.js`（依赖 `work/bulkref` 里的 net-snmp）。

#### 6.6.2 顺出来的真 bug：OID 不能用字符串比大小

代理合规之后，自检跑"GETBULK vs GETNEXT 同一份真机 walk"，结果**不一致**：

| 分类 | GETNEXT | GETBULK（修复前） |
| --- | --- | --- |
| 接口 | 26 行 | **9 行** |
| MAC | 10 行 | **6 行** |
| 资源 | 8 行 | 7 行 |

根因在 `SnmpV2cClient.WalkAsync` 的 GETBULK 单调前进保护（附录 A#12）：

```csharp
if (string.CompareOrdinal(value.Oid, last) <= 0)   // ← 错：OID 是"按段数值"排序，不是字符串序
```

接口索引从 `.9` 到 `.10` 时，按字符比 `".10" < ".9"`（`'1' < '9'`），于是这一步被误判成"没有前进"，
**整个 WALK 当场终止**。表现：ifName 表 26 个接口只剩 9 个，而查询状态照样显示"查询成功"——
典型的**静默截断**（比报错更危险）。

修复：

1. 新增 `SnmpV2cClient.CompareOid`：逐段**按数值**比（`9 < 10` 成立），非数字段才退回字节比较；
2. 单调前进保护命中时**不再把已拿到的一半当结果返回**，而是标记该目标不支持 GETBULK 并**退回 GETNEXT 重走整棵子树**；
   中途超时（`TryBulkStepAsync` 返回 null）同样退回重走，而不是返回半张表。

修复后自检：**62/62**，GETBULK 与 GETNEXT 逐行一致（54/54 行，`GETBULK 成功步数=42`）。

#### 6.6.3 仍然开着的开关（需要现场条件）

`SnmpV2cClient.BulkEnabled` 默认仍是 `false`。已具备的条件：合规代理（第三方验证过）+ 真机 walk 上逐行一致 +
永久回归场景。**还缺**：在一台真机上确认 GETBULK 与 GETNEXT 结果一致；当前开发环境尚无可用的 UDP 161 测试通路。
UDP 161 通路现在不必依赖运营商/映射方改造：用 `new-chat/SnmpTunnel`（在只有 TCP 的端口映射上转发 SNMP）
从 `127.0.0.1:161` 查询即可，助手侧无需改动（见该目录 README 第 2 节）。
